## 项目概况

- 项目：贪吃蛇游戏（浏览器端经典小游戏）
- 仓库：jinpeng-vnode/snake-game
- 运行方式：双击 `index.html`，无需服务器或构建工具

snake-game/

└── 公共/         # 共享规范

## 核心约束

1. 零依赖：不使用任何第三方库或框架
2. 双击可用：`file://` 协议下正常运行，禁止 ES Module
3. 单页面：所有状态（开始 → 游戏中 → 结束）在同一页面切换
4. 固定画布：400×400px，20×20 网格，每格 20px
5. 固定速度：200ms/帧，不随分数变化

## 文件命名规范（所有角色必须遵守）

### 开发层级定义

| 层级 | 说明 | 包含角色 |
|------|------|----------|
| **L1** | 无前置依赖，最先开发 | 产品经理、架构师、UI设计员 |
| **L2** | 依赖 L1 完成 | 前端开发者、后端开发者 |
| **L3** | 依赖 L2 完成 | 审查员、测试人员、运维 |

### GitHub Issue 标题格式

- **格式**: `L{N} TASK-{XXX}: {任务描述}`
- **示例**: `L1 TASK-001: 贪吃蛇游戏架构设计`
- **禁止**: 在标题中包含角色名称（通过标签区分角色）

### 文件命名格式

- **设计文档**: `design/L{N}-TASK-{XXX}-{模块名}.md`
- **UI规格文档**: `design/ui/L{N}-TASK-{XXX}-{页面名}.md`
- **代码文件**: 按常规命名，但注释中引用设计文档时使用完整L{N}前缀

### 文档标题格式

```markdown
# L{N}-TASK-{XXX} {模块名} 设计文档
# L{N}-TASK-{XXX} {页面名} UI 规格
```

## Git 提交（强制规则，所有角色必须遵守）

- 格式：`<type>(<scope>): <简短描述>`
- type：fix / feat / docs / refactor / security / test / ci
- **⚠️ 每完成一个文件（设计文档、代码文件、配置文件等）就立即执行：**
  ```bash
  git add -A && git commit -m "<type>(<scope>): <描述>" && git push
  ```
  **不要攒到最后一起推。** 这样即使中途断网或 AI 对话中断，已推送的部分不会丢失。
- 开发完成时用 `git status` 确认工作区为 clean，如有遗漏立即补提交

## 质量门控（阶段流转条件）

### 通用自检清单（所有角色必须检查）

- [ ] Issue标题是否符合 `L{N} TASK-{XXX}: {任务描述}` 格式？
- [ ] 文档命名是否符合 `design/L{N}-TASK-{XXX}-{模块名}.md` 格式？
- [ ] 是否通过标签而非标题来区分角色？
- [ ] 文档标题是否包含正确的L{N}前缀？
- [ ] 代码注释中引用设计文档时是否使用了完整L{N}前缀？

每个阶段必须满足门控条件才能流转到下一阶段，不满足则退回。

| 阶段流转 | 门控条件 |
|----------|----------|
| 待拆解 → 待设计 | 每个子任务有明确的验收标准（可验证的条件，不是模糊描述） |
| 待设计 → 待开发 | 设计文档包含完整接口签名（参数类型+返回类型）、文件结构、模块依赖 |
| 待开发 → 待审查 | 代码能编译/运行、所有接口与设计文档一致、有基本错误处理 |
| 待审查 → 待测试 | 审查清单全部通过、无"必须修改"项 |
| 待测试 → 已完成 | 所有验收标准对应的测试用例通过 |

**退回规则：** 任何阶段发现不满足上游门控条件，`gh issue comment` 说明具体缺失项，改 label 退回上一阶段。

## 自检规则（所有角色通用）

每个角色在提交产出前，必须执行自检：

```
<self_check>
1. 我的产出是否完整覆盖了任务要求的每一项？（逐条对照验收标准）
2. 我的产出是否有遗漏的边界情况？
3. 我是否越界做了不属于自己角色的事？
4. 我的产出格式是否符合规范模板？
5. 下游角色拿到我的产出，能否直接开始工作，还是会有疑问？
</self_check>
```

如果第 5 条答案是"会有疑问"，说明产出不够完整，需要补充。

## 思考链规则（所有角色通用）

处理任务时，先思考再行动，按以下顺序：

```
<thinking>
1. 【理解】这个任务要我做什么？验收标准是什么？
2. 【分析】现有代码/文档的现状是什么？有哪些约束？
3. 【方案】我打算怎么做？有几种方案？选哪个？为什么？
4. 【风险】这个方案有什么风险或遗漏？
5. 【执行】开始执行
</thinking>
```

不需要把思考过程写到产出文件里，但必须在内部完成这个推理过程。

- 每个角色开始任务时更新"当前任务"为进行中

## 启动流程（所有角色必须遵守）

**第一步永远是查 Issue，不要扫描代码库。**

1. 执行自己角色的 `gh issue list` 命令获取待处理任务
2. 读取任务对应的设计文档（`docs/设计/` 或 `design/ui/`）获取上下文
3. 只读取与当前任务直接相关的代码文件，不要全局扫描

❌ 禁止：启动后先扫描整个代码库、读取所有配置文件、"了解项目结构"

## 异常处理

### 开发层级（L1/L2/L3）

Issue 标题前的 `L1`/`L2`/`L3` 表示开发层级：

- **L1**：无前置依赖，最先开发
- **L2**：依赖 L1 完成后才能开发
- **L3**：依赖 L2 完成后才能开发
- **同层级的任务可以并行开发**，不同层级必须按顺序
- 开发者优先领取当前可执行的最低层级任务

### 并行开发规则

当多个开发者实例同时工作时，遵循以下规则：

**文件所有权**

- 每个模块/页面有且只有一个负责人，由架构师在设计文档的"模块分配表"中指定
- 共享文件（如 router.py、main.ts）由架构师指定唯一负责人
- 如果两个开发者都需要改同一个文件 → 架构师必须在设计文档中拆分职责，或指定一方负责

**Git 分支策略**

- `main`：稳定分支，只接受从 dev 合并，测试全部通过后由运维合并
- `dev`：开发主线，所有角色的 PR 都合并到 dev，审查员和测试人员在 dev 上工作
- `feat/{角色名}`：各角色的工作分支，从 dev 创建，完成后发 PR 到 dev
- 每个角色在自己的分支工作，包括 PM（PM 分支用于提交 PRD 文档和 docs 初始化）
- 开发完成后发 PR 到 dev，审查通过后合并
- 合并前必须 rebase dev，自行解决自己模块内的冲突

**跨模块依赖**

- 如果模块 A 依赖模块 B 的接口，但模块 B 还没开发完：
  1. 模块 A 按设计文档中的接口签名写代码（签名已确定）
  2. 在代码中标注 `# TODO: 等待 {模块B} 完成后集成测试`
  3. 不要自己写 mock 实现来替代其他模块

### Git 冲突

1. 先 `git stash` 保存本地修改
2. `git pull --rebase`
3. 如果冲突在自己负责的文件 → 自行解决
4. 如果冲突在别人的文件 → `gh issue comment` 通知对方，等待解决

### GitHub CLI 失败

1. 检查网络连接，重试一次
2. 仍然失败 → 将操作内容记录在 git commit message 中，后续补录到 Issue
3. 继续执行后续工作，不要因为 Issue 操作失败阻塞产出

### 找不到配置文件

- 设计文档不存在 → `gh issue comment` 通知架构师/UI设计员，不自行猜测
